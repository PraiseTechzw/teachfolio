## Defects addressed during this audit

- **High — evidence tenant boundary:** an identity without an institution assignment could reach evidence authorization paths too broadly. Downloads now require an active institution context, scope the file and entry to that institution, and apply owner/reviewer/administrator policy checks.
- **High — upload memory and validation:** uploads previously buffered the full request. Uploads now stream to private storage, enforce the 25 MiB limit and supported file signatures, and remove the stored object if metadata persistence fails.
- **High — public bucket misconfiguration:** server storage operations now verify that the evidence bucket is private before upload or signed download.
- **Medium — spreadsheet formula injection:** CSV cells are escaped and formula-prefixed values are neutralized.
- **Medium — placement assignment workflow gap:** institution administrators and coordinators can create and manage placements and reviewer assignments in the app.
- **Medium — reset URL behind TLS proxy:** password reset URLs now use a validated same-origin request URL and preserve HTTPS when terminated at a proxy.
- **Low — test environment fragility:** Vitest gets a test-only session secret, so tests do not depend on a production `.env` file.
- **Medium — outage-only sample portfolio:** the student portfolio previously substituted fictional records when the API failed. That fallback is removed; a failed or unauthorized request now shows an explicit error state, and the add action stays hidden until data loads successfully. A component regression test covers a 503 response. The explicitly connected fictional demo tenant and `seed:demo` utility remain labeled and intentional.
- **Low — misleading upload failure label:** an unavailable backend/storage error was labeled “DEMO MODE.” The UI now says the operation was not confirmed and advises checking the saved record before retrying.
- **Medium — readiness probe:** `/api/health` remains process-only liveness; `/api/ready` now checks a database `SELECT 1`, returns 503 on failure, and never includes connection details in its response. Docker and Render use the readiness path. Auth and Storage require separate checks.

## Post-audit verification and release blockers

- **Connectivity diagnosis:** `DATABASE_URL` and `SUPABASE_URL` are configured, but DNS resolution returned `ENOTFOUND` for both hosts in the previous run and again in this run. DNS also failed for `supabase.com` and `google.com`; therefore this execution environment has no working DNS resolution. Hostnames, credentials, and connection strings were not printed. This does not prove Supabase is unavailable or misconfigured. Repeat the generic-status diagnostic in [docs/staging-deployment.md](staging-deployment.md) from the staging host/operator network before changing project configuration.
- **Live database, Storage and end-to-end journeys:** blocked by DNS. No schema introspection, RLS policy query, migration, storage metadata request, upload, media playback, multi-account boundary test, invitation delivery, review/notification flow, or database-backed CSV export was run. Use a non-production Supabase project and separate student, assigned reviewer, unassigned reviewer, and other-institution accounts before release.
- **Invitation email:** not implemented. The administrator UI explicitly says no email is sent and the API returns `delivery: "manual"`; invitations must be shared through an approved secure channel. Configure and test an email provider/transactional delivery flow before claiming automated invitations.
- **Upload resilience:** progress reporting and cancellation are present in the browser XHR. Resumption/retry is not. MP4 uploads are limited to 25 MiB; decide whether that cap meets teaching-video requirements or implement a resumable Supabase upload flow and test interruption/recovery in staging.
- **Browser accessibility:** Chrome rendered the signed-out auth page at 390px and 1440px. Inspection was visual/DOM only; this was not a keyboard-completion, screen-reader, contrast, or automated accessibility audit. Dashboard browser testing needs a reachable backend and test accounts.
- **Bundle:** lazy loading reduced the initial JS transfer, but the 809.47 kB main chunk remains above Vite's 500 kB threshold. Continue only with measured chunk analysis and regression checks; the split workspace/editor chunks currently build successfully.
- **Safe staging verifier:** `pnpm verify:staging` requires explicit `STAGING_DATABASE_URL`, `STAGING_SUPABASE_URL`, `STAGING_SUPABASE_SECRET_KEY`, and `STAGING_CHECK_CONFIRMATION=I_CONFIRM_READ_ONLY_STAGING_CHECKS`. It inspects the database in a `READ ONLY` transaction and sends an authenticated Storage metadata GET. It does not read `.env`, apply migrations, or write data. With staging variables removed, the package command was run and exited at the safety confirmation gate before any service request; no live verifier run is claimed. Four unit tests cover its table/RLS/grant and bucket checks.
- **Staging acceptance runbook:** follow [docs/staging-acceptance.md](staging-acceptance.md) for staged setup, synthetic test accounts, authorized/unauthorized cases, core journeys, accessibility, retention, and sign-off. These are instructions, not test results.
- **Staging host preparation:** [docs/staging-deployment.md](staging-deployment.md) recommends a Render Docker web service and documents current runtime variables and external setup. `render.yaml` is not connected to a Render account and has not been applied; no staging or production deployment is claimed.

### Release blockers

1. Restore service connectivity and verify schema, deployed RLS configuration, and private storage bucket against a staging project.
2. Complete student/reviewer/admin end-to-end tests, including forbidden cross-institution access, MP4 byte-range playback, review notifications, invitations, and real CSV contents.
3. Decide and verify invitation email delivery and video upload size/resumability requirements.
4. Complete keyboard and assistive-technology review of authenticated dashboard workflows before production use.
5. Connect the repository to the Render account (or select another Docker host), configure a reachable staging Supabase project, and complete staging acceptance. Then select/configure a production provider/domain and verify HTTPS, production secrets, monitoring, backup/restore, and rollback. The prepared Render staging Blueprint has not been applied and no deployment was available in this run.

## Release decision

No migration, live RLS/grant inspection, Storage request, account journey, or end-to-end data flow was executed. The app was not deployed; the Render Blueprint is prepared but not connected to a provider account. Production domain, secrets, backups, monitoring, and rollback are not configured here. Reassess after the staging runbook has been completed and signed off, then complete the production deployment gates above.
