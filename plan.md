# Implementation Plan — Student Teacher E-Portfolio System

## Product and technical approach

Deliver a connected, responsive portfolio application in the initialized WebDev project, retaining its actual React 19 + Vite + TypeScript frontend, Wouter routing, Tailwind/shadcn-style components, Express + tRPC server, Drizzle ORM, and managed MySQL database. Do not replace this working architecture with the brief's preferred Next.js/Supabase stack. Inspect and preserve the existing Manus OAuth and server-side session validation; OAuth establishes identity only, not application access. A user's application account must be explicitly activated and assigned least-privilege roles by an authorized administrator before protected data is accessible. New, inactive, unassigned, and suspended accounts are denied by default. Users cannot select or change their own role; provide no fake login, demo-auth bypass, or client-only authorization. The starter already sets its session cookie to `SameSite=None; Secure`, as required for HTTPS Preview embedding.

Enforce authorization in every protected tRPC procedure, server endpoint, database access path, and upload/preview/download operation. Scope queries and mutations by institution and authorized record IDs, and verify ownership or explicit supervisor/lecturer assignment; never trust a client-supplied tenant or role. Institution administrators may manage only their own institution. Platform-wide administration requires a separate, explicitly provisioned platform-admin permission; do not infer institution or platform privileges from OAuth identity or project ownership. Inspect and remove or constrain the starter's existing `ownerOpenId` → generic `admin` promotion so it does not silently grant application privileges. The first platform administrator must be explicitly provisioned through a trusted server-side bootstrap configuration/operation; if that provisioning is absent, remain default-deny rather than presenting an insecure admin-creation shortcut. Keep authorization policy centralized in server helpers and fail closed when tenant, account status, role, or assignment context is missing. Audit account activation/deactivation, role changes, placement/supervisor assignment changes, assessment decisions, and other sensitive administrative actions. If the current framework cannot enforce one of these controls, document that limitation rather than implying it is secure.

Treat the database as shared by development and published runtime: use reviewed additive migrations, avoid destructive schema changes, and make fictional demonstration records clearly identifiable and safely initialized without overwriting user edits. The project has a real managed MySQL capability; use it for application persistence rather than representing browser-local demo state as secure server storage. Seed only fictional Zimbabwean education records and no identifiable children.

Build reusable page/shell/form/status/table patterns around a responsive role-aware navigation. Implement high-value connected journeys first: student dashboard and portfolio requirements; create/save/reopen/submit a structured lesson plan; immutable submission versions and a reviewer queue with feedback/revision/approval history; reflections; evidence metadata and validated upload states; notifications; placement context; and progress/reporting derived from configured requirements and records. Add schemes of work, assessments/rubrics, staff/coordinator/admin views and safe exports through shared modules. Support search, status/category filters, useful loading/empty/error/success states, mobile forms, print views, and authorized CSV exports where implemented. Use explicit non-production/demo labels and never claim an unsupported integration succeeded.

Evidence uploads must validate size/type and privacy/consent before any transfer. Use the platform's private object-storage presign API only when its server-side runtime credentials and endpoint are actually available; persist metadata only after a successful byte transfer. Authorize every upload, preview, and download against the authenticated account, institution, role, and owning/assigned record. If unavailable, clearly report the upload limitation and do not fabricate a completed upload. Never expose credentials or signed private URLs to the client. Do not claim email/SMS delivery or legal compliance. Use configurable institutional requirements, assessment scales, deadlines, and retention settings rather than official hardcoded grading rules.

## Main project structure

- `client/src/App.tsx`: authenticated route table and role-aware application shell.
- `client/src/pages/`: dashboard, placement, portfolio, schemes, lesson plans, reflections, evidence, submissions, feedback, notifications, reports, settings and administration/reviewer pages; reuse templates for detail/form views.
- `client/src/components/`: shared navigation, responsive tables/cards, status labels, validation, confirmations, review controls and accessible feedback patterns.
- `client/src/lib/`: tRPC client helpers and presentation utilities.
- `server/routers.ts` plus focused feature modules under `server/`: validated tRPC APIs and fail-closed authorization for portfolio, lessons, schemes, journal, evidence, review, assessment, placement, notifications, admin and reports.
- `server/authz/` (or equivalent focused server module): shared authentication-state, institution scope, role/permission, record ownership, assignment and platform-admin guards; apply these to every protected procedure and endpoint.
- `server/db.ts`: typed Drizzle operations with institution/record predicates enforced on reads and writes; never authorize based solely on client-supplied record IDs or tenant IDs.
- `server/_core/`: preserve supplied OAuth/session and server setup; allow authenticated identity but deny protected application access until administrator activation/role assignment; add protected storage endpoints only if the platform storage capability is present.
- `drizzle/schema.ts`, `drizzle/relations.ts`, and additive `drizzle/` migrations: users/profiles with active/suspended state and administrator-assigned roles, institution/programme/cohort/academic periods, schools/classes/subjects/placements/assignments, portfolios/requirements, schemes and weekly rows, plans and stages, reflections, institution-scoped evidence metadata, immutable submission versions, reviews/comments, rubric criteria/results, notifications and audit history. Include tests for default-deny behavior and cross-institution ID substitution.
- `public/manus-routes.json`: synchronized manifest of actual frontend routes before the first development-server start.
- `plan.md`, `TODO.md`: project plan/design and complete product outcome criteria/progress.

## Design direction

Reuse the brief's chosen visual direction: a premium, calm academic-management interface, not a generic marketing landing page.

- **Design movement:** Contemporary editorial academic software—precise, practical, and quietly authoritative.
- **Core principles:** (1) Clear work status at a glance. (2) Dense review information with generous breathing room. (3) Forms that guide completion without obscuring real work. (4) Privacy and accessibility are visible parts of the workflow.
- **Color philosophy:** Warm white and pale neutral surfaces keep long-form planning readable; deep ink/navy anchors authority; restrained indigo/blue identifies actions; green/amber/red communicate approved/pending/attention states, always paired with text labels.
- **Layout paradigm:** A persistent, narrow navigation rail with a wide document/workspace canvas; dashboards use compact summary bands and aligned activity/review lists rather than oversized hero cards; mobile collapses to a drawer and stacks the task content.
- **Signature elements:** A small folio-tab motif for portfolio categories; a slim, consistent status rail on submitted work; a compact “teaching week” index for planning tables.
- **Interaction philosophy:** Predictable controls, explicit save/submission feedback, deliberate confirmation for consequential review decisions, and no silent mutation of reviewed versions.
- **Animation:** Minimal and functional only: short opacity/position transitions for drawer/dialog and status feedback; honor reduced-motion preferences; avoid animated dashboard decoration.
- **Typography system:** Inter (or an existing locally available sans-serif) for interface and forms; a restrained serif such as Source Serif 4 only for report/print titles if reliably available. Use clear 12–14 px secondary labels, 14–16 px body, and concise 22–30 px page headings; never depend on color alone.
- **Brand essence:** A dependable teaching-practice record for student teachers and their reviewers; **structured, supportive, accountable**.
- **Brand voice:** Direct, encouraging, and precise. Example: “Your next review is one lesson plan away.” “Returned for revision — open the feedback before you resubmit.”
- **Wordmark & logo:** A simple folio/check mark built from two offset page outlines, paired with a compact “Teachfolio” wordmark; use it as a small product identifier, not an oversized hero graphic.
- **Signature brand color:** Indigo `#3F51B5`, used sparingly for primary actions and active navigation.

## Delivery boundaries

The initial implementation is a functional prototype on the managed project stack, not a claim of production compliance. Real OAuth, database-backed data, and private uploads depend on the runtime services actually being reachable. Storage may be unavailable even with database/server selected, so the UI must report that honestly. Email/SMS, verified legal compliance, malware scanning, background video processing, external institution integrations, and operational backup/retention services must not be claimed unless separately configured and implemented. Do not expose sensitive portfolio demo data to an unactivated/unassigned user simply to make the dashboard appear populated. Exercise authorization boundaries with server-side tests, including changed-ID attempts to access another institution's records and assigned-reviewer boundaries. Preserve the brief's role and privacy rules in implemented paths; identify incomplete breadth explicitly at handoff.


## Implementation status and evidence

The initialized architecture has been retained. The main implemented modules are `client/src/App.tsx` (OAuth-aware, default-deny shell), `client/src/pages/Workspace.tsx` (role-scoped dashboards, lists, reviews, reports and administration), `client/src/components/PortfolioFormDialog.tsx` (portfolio forms and explicit evidence transfer), `server/authz.ts` and `server/authz-policy.ts` (fail-closed server policy), `server/routers.ts`/`server/db.ts` (tenant-scoped procedures and persistence), `server/portfolio-validation.ts` (server-side scheme/lesson/reflection/evidence submission rules), `server/evidence-policy.ts` (upload signature/type/size checks), `server/_core/csrf.ts` plus `server/_core/index.ts` (session-bound write token and transfer route), `server/evidence.ts` (private evidence endpoints), `drizzle/schema.ts` plus additive migration, and trusted operator scripts under `scripts/`. Student portfolio surfaces are routed through `client/src/components/StudentPortfolioModule.tsx`, forms use `PortfolioFormDialog.tsx`, and structured detail/version output uses `PortfolioRecordDetails.tsx`. The actual route declarations are in `client/public/manus-routes.json`.

The reviewed additive migrations have been applied to the initialized managed database and the explicitly requested fictional Zimbabwean demonstration tenant has been seeded. Seeded demo identities use a reserved OpenID prefix actively denied by server-side application authorization even if presented in a signed session; records remain visible only to genuinely authorized accounts. The latest TypeScript check, all 35 tests in 6 test files, and production build pass. `/api/health` and the 19-route JSON manifest returned HTTP 200; anonymous CSRF-token access returned 401. Earlier anonymous evidence-download verification returned 403. A read-only runtime check confirmed the managed database, fictional demo tenant and private-storage configuration are present without exposing credentials. The isolated browser confirmed the OAuth/default-deny screen; no authenticated student/reviewer session was available for mutation or transfer testing. Presigned storage GET URLs are used only within the server; after record authorization, the server streams bytes with no-store headers and never returns the bearer URL to the browser. Platform-wide audit reads require the explicit platform-admin assignment, institution audit reads are tenant-scoped, and invitation activation audits identify the redeeming OAuth account.

Phase 4 adds `server/review-workflow.ts`, assignment-scoped review queue and decision procedures in `server/routers.ts`, the reviewed JSON rubric snapshot migration in `drizzle/0002_review_rubric.sql`, and the reviewer/history components `ReviewQueueDashboard.tsx` and `ReviewHistoryTimeline.tsx`. Six workflow tests cover assignment/self-review policy, score validation, snapshot immutability, and submit → revision request → resubmission → approval. The review mutations atomically guard current record/version state and write decision, version outcome, rubric, notification and audit records. Review endpoints are limited to assigned supervisors/lecturers; detail responses and evidence downloads are constrained to immutable submitted versions. The rubric is versioned and formative, with 10 criteria scored 1–4; institution-specific criterion/scale/weight configuration remains incomplete. Signed-in route-to-database lifecycle verification, concurrent database decision testing, and endpoint-level cross-tenant ID-tampering tests were not available in this run.

Delivery remains a prototype. Structured weekly schemes, dynamic lesson-stage forms/duration validation, reflective-journal forms, evidence metadata/upload workflow and submission history were implemented using the existing JSON schema and APIs; scheme/detail print is available through browser print. However, signed-in save/reopen, actual file transfer/preview, submission/revision/resubmission and reviewer handoff were not end-to-end exercised because no authenticated user session was available. Endpoint/database integration coverage for changed-ID tenant boundary attempts remains outstanding. Configurable assessment rubric scores/weights, placement and institution academic-structure administration, complete supervisor dashboards, comprehensive exports/filters, deadlines/overdue automation and retention controls remain incomplete. Email/SMS, legal compliance and production readiness are not claimed. Keep the approved default-deny/authentication/institution security rules in force while closing remaining product scope; never use seeded demo identities or a client role control as a substitute for an authorized account.
