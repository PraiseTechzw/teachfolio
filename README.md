# Teachfolio

Teachfolio is a student-teacher teaching-practice portfolio built with React, TypeScript, tRPC, Drizzle and Supabase. Supabase Auth handles accounts, Supabase Postgres stores application records, and a private Supabase Storage bucket holds evidence media.

## Supabase setup

Create a Supabase project, then copy `.env.example` to `.env` and fill in:

- `SUPABASE_URL` and the **publishable** key from the project API settings.
- The server-only **secret** key. Never add this key to client code or expose it to users.
- The PostgreSQL connection string from Project Settings → Database. Keep `sslmode=require` enabled.
- A random `SESSION_SECRET` of at least 32 bytes, used to sign CSRF tokens.

In Supabase Auth, enable email/password sign-in and email confirmation. Set the Site URL to the app's public origin and add that origin plus `<APP_BASE_URL>/?invite=*` to the allowed redirect URLs so pending invitation links survive signup confirmation and password recovery. Supabase Auth supports wildcard redirect patterns; keep the wildcard limited to the invitation query pattern. See [Supabase redirect URL guidance](https://supabase.com/docs/guides/auth/redirect-urls). In Storage, create a **private** bucket named `teachfolio-evidence`, set its size limit to 25 MiB, and allow PDF, DOCX, XLSX, PPTX, JPEG, PNG, and MP4 MIME types. Keep the bucket private: the backend checks this setting before upload and signed downloads. Evidence access is checked by the server against institution, placement assignment, ownership, and submitted-version history; the server secret bypasses Storage RLS and must remain private. Uploads are streamed through the server with a 25 MiB cap. Images preview in the record; MP4 playback uses authenticated byte-range requests. See [Supabase Auth server guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), and [private downloads](https://supabase.com/docs/guides/storage/serving/downloads).

## Email delivery

Teachfolio uses Resend for invitation and account-activation emails, plus email copies of portfolio review and placement notifications. Set `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, and `APP_BASE_URL` in the server environment. Verify the sender domain in Resend and publish the DNS records Resend provides before sending from that domain. `RESEND_FROM_EMAIL` should be an address on the verified domain, for example `Teachfolio <noreply@your-domain.example>`. `APP_BASE_URL` is the public HTTPS app origin in staging/production; it is used to build invitation and notification links. Never put the Resend key in client code or source control.

Supabase Auth sends account-confirmation and password-recovery messages. To send those through Resend too, configure the Supabase project's Auth SMTP settings: host `smtp.resend.com`, port `465` (or `587` with TLS), username `resend`, password the Resend API key, and the same verified sender address. Set Supabase Auth's Site URL and allowed redirect URL to the `APP_BASE_URL` origin. Confirmation and recovery codes/links are generated by Supabase Auth; Teachfolio does not create or store authentication codes. If direct Resend delivery is unavailable, invitation creation returns a one-time token for secure manual sharing and the in-app notification remains available. Email acceptance by Resend does not guarantee inbox delivery, so verify delivery in the Resend dashboard during staging acceptance.

The PostgreSQL tables have RLS enabled, but this application does not configure per-user Postgres policies or send browser queries to those tables. The server connects with a privileged database role and enforces authorization in its tRPC and evidence routes. Keep `DATABASE_URL` server-only. Do not add browser access to application tables or switch the server to a non-bypassing database role without adding and testing transaction-scoped RLS policies first. The Storage bucket remains private and has no public-object access policy.

## Install and run

Requirements: Node.js 22 or newer and pnpm 10.

```sh
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm dev
```

Open `http://localhost:3000`. New accounts use Supabase Auth email/password and must confirm their email when confirmation is enabled. Account creation does not assign an application role. Access is granted only after an administrator-issued invitation is redeemed by the matching email account.

## Access bootstrap

The first platform administrator must be provisioned by a trusted operator after the target user registers and signs in. Verify that user's `openId` in the `users` table, set it in a local shell variable, then run this server-side against the configured Supabase database:

```sh
REGISTERED_USER_OPEN_ID='replace-with-the-verified-users.openId'
pnpm provision:platform-admin "$REGISTERED_USER_OPEN_ID" --confirm-trusted-platform-admin
```

This adds a platform-wide assignment and audit record. Never expose the command through a public endpoint. Platform administrators create institutions and issue invitations. Institution administrators can invite users only to their institution. Invitations are single-use, role- and institution-bound, expire after seven days, and match the exact email. Resend sends an invitation link when configured; if sending cannot be confirmed, the administrator receives a token to share through an approved secure channel.

For fictional sample data, run `pnpm seed:demo --confirm-fictional-demo-seed`. This initializes a reserved demo institution and fictional records; it does not create a demo login or upload files.

## Commands and migrations

- `pnpm dev` — development server
- `pnpm build` / `pnpm start` — production build and server
- `pnpm check` — TypeScript check
- `pnpm test` — application unit tests (uses a test-only CSRF key; no production `.env` is required)
- `pnpm verify:staging` — read-only staging schema, RLS/grant, and private Storage checks; requires explicit `STAGING_*` variables
- `pnpm db:generate` — generate a Drizzle PostgreSQL migration
- `pnpm db:migrate` — apply generated migrations

Follow the [staging acceptance checklist](docs/staging-acceptance.md) before accepting a staging release. The verifier does not run migrations or modify database/storage data.

For the Docker runtime, Render staging Blueprint, required environment variables, region/hosting recommendation, DNS diagnosis, migration precautions, Auth setup, and end-to-end staging sequence, follow the [staging deployment guide](docs/staging-deployment.md). `/api/health` is a process liveness endpoint; `/api/ready` checks database readiness and returns only a generic status. Neither endpoint proves Auth, Storage, or user workflow availability.

The checked-in application schema is now PostgreSQL. Old MySQL migration files under `drizzle/` are historical and must not be applied to Supabase. Review generated SQL before applying it to a live project. The app does not automatically copy data from a former MySQL database; migrate any existing records separately before switching production traffic.

The prototype implements institution-scoped roles, invitation activation, portfolio submissions, reviewer workflows, private evidence authorization, notifications and CSV reporting. It does not claim legal compliance or institutional accreditation. Do not upload identifiable learner media without required school and guardian consent. Configure backups, monitoring, retention, consent procedures and incident response before real student use.
